# 从手写草稿到能分享的海空战组件

这次先把东西做得好用。斜面只能朝一个方向，搭炮塔就得反复绕路；炮声离开原工程就丢了，分享文件也就少了一半意义。这些问题看起来小，却直接决定制作者愿不愿意继续做下去。

手绘炮塔的思路很清楚：方向机负责左右，高低机负责俯仰，炮管有自己的口径和倍径。实现时把这三个关系分开，炮口位置就能跟着真实的旋转结果走，试射和战斗也能使用同一套数据。斜面朝向跟随镜头，再保留 R 键调整，比继续增加一排角度输入框更省事。

炮管不用做得很夸张。炮闩一端稍粗、炮口一端稍细，加上内壁和凹进去的暗膛，已经比实心圆柱可信不少。细节要让人看得出来，也要控制面数，毕竟海战不是只摆一座炮塔。

大和和南达科他先作为可以拆改的样板。主炮布局、分层舰桥、桅杆、烟囱和船体比例要有区别，不能只是换个名字。当前采用低面数方块近似，细节仍有继续打磨的空间，也不把它说成精确复原。样板的作用是让新用户打开工程就有东西可看、可改、可试。

海图也一样。不是岛越多越好，先把航道留出来，把水面、尾迹、射击和起降跑稳。主战区边界需要和后方航母的补给路线一起考虑，否则地图看似完整，飞机却飞不到补给点。

照片槽位来自另一张草稿。名单适合查参数，阵型适合看位置，两者可以同时保留。照片在保存时由程序拍摄，和载具文档放在一起，不再往素材库塞一批用户并没有主动导入的小图片。炮塔的分享文件也要把炮声带走，导入时重新分配素材编号，省掉玩家自己找文件的麻烦。

验证不能只看窗口里有没有按钮。这版检查了保存、重开、独立导出、导入后素材引用，以及导出的游戏。最终结果和截图保存在本地验证记录中；公开源码由 GitHub 工作流继续构建和测试。

作者提供的四张原始手稿见[草稿索引](design-sketches/README.md)。它们保留了最初的想法，也方便之后开发时检查有没有把交互做复杂。
